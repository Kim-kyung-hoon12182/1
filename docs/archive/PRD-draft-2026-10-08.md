## 1. 배경

![배경 통계 요약](../charts/background-stats.png)

차트 생성: `charts/make_background_chart.py`. 차트에 있는 숫자는 표로 다시 쓰지 않고, 출처는 부록 번호로 연결합니다.

### 1-1. AI는 이미 반복 업무에 쓰이고 있다

직장인 94.9%가 업무에 AI를 쓰고 [B-2], 설문 응답자 22/24명이 같은 작업을 AI에 여러 번 요청해봤습니다. [A-2] 반복 업무는 업무보고, 자료 요약, 회의록, TIL·블로그처럼 형식이 정해진 문서가 많았습니다. [A-1]

### 1-2. 그런데 결과를 확인하고 고치는 데 시간이 든다

97.5%가 AI 결과물을 검증·재편집하고, 56%는 자주·항상 확인하며 주 평균 2시간을 씁니다. [B-1] 설문에서도 AI를 덜 쓰게 된 이유 1위가 확인·수정 시간(12/24명)이었습니다. [A-2]

### 1-3. 고쳐야 하면 AI를 쓴 시간 이득이 사라진다

AI 결과가 수정 없이 맞는 경우는 37%입니다. 고쳐야 할 때 직접 하는 것과 시간이 같다는 응답이 46%, 더 걸린다는 응답이 11%로, 57%는 시간 이득이 없습니다. [B-1] 설문에서도 "매번 수정해야 함" 8명, "요청을 매번 다시 입력" 7명이 AI를 덜 쓰게 된 이유로 꼽았습니다. [A-2]

### 1-4. 결과를 믿기 어렵고, 언제 믿어야 할지도 모른다

AI 활용의 가장 큰 어려움은 결과 신뢰성 부족(42.4%)이고, 51%는 언제 믿고 언제 확인할지 항상 알지는 못합니다. [B-2] 설문에서는 10/24명이 결과를 신뢰하기 어렵다고 답했습니다. [A-2]

### 1-5. 저장·메모리 기능이 있어도 해결되지 않는다

같은 작업을 다시 시킬 때 22명 중 12명(54.5%)은 저장 없이 같은 대화방에 이어 쓰거나(6명), 매번 새로 쓰거나(3명), 예전 내용을 찾아 복사했습니다(3명). [A-3]

- OpenAI도 프로젝트·맞춤 지시 같은 고급 기능은 파워 유저 위주로 쓰이고, 설정 부담이 장벽이라고 밝혔습니다. [B-3]
- 기능을 쓰는 사람들도 "맞춤 지시를 넣어도 매번 다시 붙여야 한다", "고쳐도 같은 실수가 돌아온다"고 말합니다. [E]

### 1-6. 자동화는 확인하고 개입할 수 있을 때 받아들인다

61%는 AI가 스스로 행동하지 않기를 원하지만, 개입할 수 있다면 70%가 자율 실행을 받아들입니다. [B-5] 실행 전 승인을 원하는 사람은 47%, 승인 없이 괜찮다는 사람은 16%였습니다. [B-5]

## 2. 핵심 문제

> 반복 업무를 AI에 맡기는 사람들은 결과를 믿지 못해 매번 전체를 확인하고 고친다. 고쳐야 하면 시간 이득이 사라지고, 다음에도 같은 설명과 수정을 반복한다. 그래서 AI에게 믿고 맡길 수 있는 상태에 이르지 못한다.

문제별 배경과 해결 가설의 연결은 0장 표에 있습니다.

**근거의 역할**

| 근거 | 보여주는 것 |
| --- | --- |
| 공개 조사, 사용자 글 | 문제가 실제로 있다 [B, E] |
| 설문 | 우리 대상 안에서 문제의 크기 [A] |
| 사용성 테스트, 엑스포 | 해결책이 문제를 줄이는지 [12장] |

## 4. 해결 가설

| 단계 | 가설 | 근거 | 근거 수준 |
| --- | --- | --- | --- |
| 1차 | 결과마다 적용 기준과 입력 근거를 보여주면, 표시된 부분만 확인할 것이다 | 설명을 보여주면 더 믿을 만한 응답 선택 2배 (165/300 대 84/300) [B-4] | 일부 (실험 환경, 틀린 근거는 역효과) |
| 2차 | 사용자가 승인한 수정 기준이 쌓이면, 반복할수록 수정량이 줄 것이다 | 수정에서 기준을 추출해 쓰면 수정량 31~73% 감소 [B-6] | 일부 (시뮬레이션) |
| 3차 | 수정 없이 쓴 기록이 쌓인 일을 제안하면, 맡기는 부담이 줄 것이다 | 언제 믿을지 모름 51% [B-2], 개입 가능 시 수용 70% [B-5] | 간접 근거만 |

### 4-1. 1차 — 확인 부담 줄이기

- 방법: 줄 단위 결과, 적용 기준, 입력 위치, 입력에 없음, 확인 필요 표시
- 검증 지표: 결과 확인에 걸린 시간 / 전체를 읽었는지 표시된 곳만 봤는지 / 근거 표시가 유용했는지

### 4-2. 2차 — 반복 수정 줄이기

- 방법: AI가 기준을 제안하고, 사용자가 승인한 것만 저장. AI가 기준을 마음대로 바꾸지 않음
- 검증 지표: 같은 일의 수정 횟수 / 2·3회차 수정 없음 비율 / 같은 수정이 반복되는 비율

### 4-3. 3차 — 확인된 일만 맡기기

- 방법: 3번 연속 수정 없음이면 제안. 회차별 예시는 5-1 표
- 3번은 검증된 값이 아니라 MVP의 임시 기준. 이후 2·3·5회를 비교
- 검증 지표: 제안을 본 뒤 맡겨보겠다는 반응 / 제안 시점이 적당했는지

## 5. 차별점

> 다른 AI는 결과를 만들어 주고, 이 서비스는 그 일을 믿고 맡겨도 되는지 알려준다.

### 5-1. 핵심: 일마다 쌓이는 수정 기록

이 서비스는 AI를 더 정확하게 만들지 않습니다. 정확도는 모델을 만드는 회사의 영역입니다. 이 서비스는 **사용자가 결과를 믿어도 되는지 판단할 수 있게** 합니다.

그 판단의 근거가 일마다 쌓이는 수정 기록입니다. 같은 일을 몇 번째부터 고치지 않고 쓰게 됐는지 기록하고 보여줍니다.

| 일: 주간보고 | 1회차 | 2회차 | 3회차 | 4회차 |
| --- | --- | --- | --- | --- |
| 결과 | 2곳 고침 → 기준 1개 추가 | 1곳 고침 | 안 고침 | 안 고침 |
| 화면 | 근거 표시로 고칠 곳 확인 | | | 한 번 더 안 고치면 맡기기 제안 |

- 문제(2장)가 "믿지 못해서 매번 확인하고 고친다"이므로, 해결도 신뢰 하나에 집중합니다.
- 51%가 언제 믿어야 할지 모른다고 답했습니다. [B-2] 수정 기록은 "언제 믿어도 되는지"에 대한 답입니다.
- 반복 업무가 대상이라 기록이 쌓입니다. 한 번 하는 조사나 질문에서는 기록이 쌓이지 않습니다.

### 5-2. 다른 서비스와 비교

개별 기능은 이미 다른 서비스에 있습니다. 다른 점은 **사용자가 결과를 고쳤는지 기록하고, 그 기록으로 맡길지 정한다**는 것입니다.

| 서비스 | 하는 것 | 없는 것 | 출처 |
| --- | --- | --- | --- |
| NotebookLM, Elicit | 답변마다 근거 문장 표시, 누르면 원문 강조 | 매번 새 질문. 같은 일이 나아지는지 기록 없음 | [C-3] |
| ChatGPT·Claude 메모리 | 기준·선호 저장 | 결과를 고쳤는지 모름. 저장해도 적용 안 된다는 VOC [E] | [C-1] |
| GPTs 빌더 | 대화로 지시문 작성 | 고쳤는지 모름. 개인 계정은 새로 만들 수 없음 | [C-1] |
| Freed, Noumi | 고친 내용을 기준으로 반영 | 그래서 덜 고치게 됐는지 보여주지 않음 | [C-2] |
| Demi | 반복되는 일을 맡기라고 제안 | 반복 횟수만 봄. 고쳤는지는 보지 않음 | [C-2] |
| ChatGPT 예약 작업 | 정해진 시간에 자동 실행 | 맡겨도 되는지 판단할 근거 없음 | [C-1] |

### 5-3. 가져오는 것과 만드는 것

검증된 방식은 가져오고, 수정 기록만 새로 만듭니다.

| 기능 | 역할 | 참고한 서비스 | 구분 |
| --- | --- | --- | --- |
| 근거 표시 (왼쪽 재료, 오른쪽 결과, 누르면 강조) | 고칠 곳을 빨리 찾아 "이대로 쓸게요"를 누를 수 있게 함 | NotebookLM, Elicit [C-3] | 가져옴 |
| 질문으로 기준 만들기 | 프롬프트를 쓰지 않게 함 | GPTs 빌더 [C-1] | 가져옴 |
| 고친 것을 기준 후보로 제안, 승인한 것만 저장 | 고칠 게 점점 줄게 함 | Noumi [C-2], Cursor [C-3] | 가져옴 |
| 일마다 수정 기록 | 줄어드는 게 숫자로 보이게 함 | — | **새로 만듦** |
| 수정 기록으로 맡기기 제안 | 기록이 충분하면 넘김 | Demi는 반복 횟수 기준 [C-2] | **기준을 바꿈** |

흐름: 확인 → 고치기 → 기준 쌓기 → 수정 기록 → 맡기기

### 5-4. 프롬프트를 쓰지 않는다

차별점이 아니라 사용 편의입니다. 사용자는 업무를 설명하고 결과를 고치기만 합니다. AI가 그걸 기준으로 정리합니다.

> 사용자: "매주 주간보고를 써. 지난주 업무 메모를 넣을 거고, 500자 정도로 팀장에게 보고하는 형태로."
>
> 생성된 기준: 500자 이내 / 지난주 완료 업무 중심 / 주요 성과 포함 / 숫자 유지 / 정중한 보고체
>
> 확인하고 저장하면 다음 실행부터 자동 적용.

## 6. 기능 요구사항

### 6-1. 일 등록 (2차 가설)

- 예시 일(주간보고, 회의록, TIL·블로그 초안, 자료 요약)을 고르거나 직접 시작한다. [A-1]
- 질문 4개에 답한다: 무슨 일인지 / 재료는 무엇인지 / 결과 모양(양식, 길이, 말투, 뺄 내용) / 예전에 잘 나온 결과(선택)
- AI가 기준 5~8개를 만들고, 사용자가 수정·삭제·추가 후 저장한다.
- 저장된 기준만 실행에 쓰인다.

### 6-2. 실행

- 일을 고르고 재료를 붙여 넣어 실행한다. 설문 20명 중 14명(70.0%)은 재료가 이미 모여 있었다. [A-4]
- 결과는 줄 단위로 나온다.

### 6-3. 결과 근거 표시 (1차 가설)

| 표시 | 내용 |
| --- | --- |
| 적용된 기준 | 줄을 누르면 그 줄에 적용된 기준 강조 |
| 입력 위치 | 줄을 누르면 재료에서 해당 부분 강조 |
| 입력에 없음 | 재료에 없는 내용이 들어간 줄 |
| 빠진 재료 | 재료에 있는데 결과에 없는 부분 |
| 확인 필요 | 근거를 찾지 못한 줄 |

- 화면은 왼쪽 재료, 오른쪽 결과로 나눈다. 결과 줄을 누르면 재료의 해당 부분이 강조된다. [C-3]
- 상태는 색만 쓰지 않고 글자 라벨을 함께 붙인다. Gemini 답변 확인 기능에서 초록색은 "웹에서 찾음"이라는 뜻이지만, 여기서는 "재료에 있음"이라는 뜻이기 때문이다. [C-3]
- AI가 준 근거 문장이 재료에 실제로 있는지 앱에서 대조한다. 실패하면 "확인 필요"로 둔다. 틀린 근거는 신뢰를 낮추기 때문이다. [B-4]
- 화면 문구는 "확인할 곳을 알려드려요"로 하고, 정확하다고 표현하지 않는다.

### 6-4. 고치기와 기준 추가 (2차 가설)

- 직접 고치거나 다듬기 버튼("더 짧게", "숫자 위주로", "말투 정중하게")을 쓴다. 수정 이유 중 일반적 표현 34%, 서식 31% [B-1]
- 고쳐서 저장하면 기준 후보 한 줄과 함께 "다음부터도 이렇게 할까요?"를 묻는다.
- [확인] → 기준에 추가 / [이번만] → 이번 결과에만 적용
- 제안은 한 줄, 한 번 클릭으로 끝낸다. 승인을 자주 묻는 방식은 번거로울 수 있다. [C-3]

### 6-5. 수정 기록 (3차 가설)

- "이대로 쓸게요" → 수정 없음, "고쳐서 저장" → 수정 있음
- 일 목록과 일 상세에 최근 기록 표시 (예: 최근 3번: 고침, 고침, 안 고침)
- 5장 차별점의 중심 기능이므로 범위를 줄일 때도 남긴다.

### 6-6. 맡기기 제안 (3차 가설)

- 3번 연속 수정 없음이면 제안 카드를 띄운다. 기준 값은 상수로 둔다.
- 문구: "이 업무는 최근 3번 연속 수정 없이 사용했어요. 이제 AI에게 맡겨보시겠어요?"
- 카드: 수정 기록, 예약 작업용 지시문(기준 + 양식 + 재료 안내), 복사 버튼, 설정 방법
- ChatGPT 예약 작업은 외부 연동 API가 없으므로 복사와 안내까지만 한다. [C-1]

## 7. 데이터 (localStorage, 로그인 없음)

```ts
type Task = {
  id: string
  name: string
  answers: { what: string; materials: string; shape: string; example?: string }
  criteria: { id: string; text: string; source: 'setup' | 'edit' }[]
  runs: Run[]
  createdAt: string
}

type Run = {
  id: string
  input: string
  output: OutputLine[]
  missing: string[]
  edited: boolean
  finalText: string
  createdAt: string
}

type OutputLine = {
  text: string
  criteriaIds: string[]
  sourceQuotes: string[]
  status: 'grounded' | 'not_in_input' | 'needs_check'
}
```

## 8. AI 호출

- `app/api/generate.ts` 서버 함수만 거친다. 키는 브라우저에 노출하지 않는다.
- 모델 `gemini-3.8-flash`, 무료 등급. 결제 정보를 연결하지 않는다.
- 실행 응답 형식:

```json
{
  "lines": [
    { "text": "", "criteria_ids": [], "source_quotes": [], "not_in_input": false }
  ],
  "missing": []
}
```

| 조건 | status |
| --- | --- |
| 근거 문장이 재료에 있음 | `grounded` |
| `not_in_input: true` | `not_in_input` |
| 근거 문장이 재료에 없음 | `needs_check` |

- 429 응답 시 "지금 사용하는 사람이 많아요. 1분 뒤에 다시 시도해 주세요."
- 입력 최대 8,000자
- 첫 화면에 "회사 기밀이나 개인정보는 넣지 마세요" 안내. 설문에서 입력 부담 7명(29.2%) [A-2]

## 10. 범위

### 10-1. 단계별 범위

| 단계 | 목표 | 기능 |
| --- | --- | --- |
| MVP 1차 | 확인 부담 감소 | 업무 등록, 기준 생성, 실행, 근거 표시 |
| MVP 2차 | 반복 수정 감소 | 수정, 기준 후보, 기준 누적, 수정 기록 |
| MVP 3차 | 맡길 수 있는지 확인 | 수정 없음 감지, 맡기기 제안, 복사용 지시문 |
| Next | 옮기기 쉽게 | 예약 작업 설정 안내 개선, 로그인과 서버 저장 |
| Future | 직접 자동화 | 자체 예약 실행, 실행 결과 알림, 예외 처리 |

이번 프로젝트의 질문은 "이 업무를 실제로 AI에게 맡길 수 있는 상태가 되는가?"이고, 실제 자동 실행은 그다음 문제입니다.

| --- | --- |

### C-3. 참고한 화면 방식

해결 가설의 근거 수준은 4장, 확인 계획은 12-2에 있습니다.
