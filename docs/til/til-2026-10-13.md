# [TIL] "더 낫다"가 아니라 "다른 질문에 답한다" — 신뢰를 다루는 서비스의 차별점 찾기

안녕하세요. 김경훈입니다.
오늘은 부스 제출을 앞두고 PRD를 최신화하고, 근거의 출처를 하나씩 다시 확인했습니다. 그러다 "결국 내 서비스가 다른 서비스보다 나은 점이 뭐지?"라는 질문에 막혔습니다. 정리해 보니 기능 하나하나는 이미 다 있었고, 차별점은 기능이 아니라 **어떤 질문에 답하느냐**에 있었습니다.

## 1. 무엇을 했는가

1. **PRD 최신화:** 배포 주소, 대상(직장인과 학생), 만들면서 확인한 숫자, 한계, 제작 회고를 반영했다.
2. **근거 출처 재확인:** 인크루트, 노션, Connext, TeamViewer 원문을 다시 열어 조사 주체, 대상, 시기를 맞췄다. TeamViewer는 10개국이 아니라 9개국이었다.
3. **문제 정의 다듬기:** 처음 쓴 문장이 "못 믿는다 → 신뢰가 떨어진다"로 같은 말을 반복하고, "보통"처럼 과하게 일반화하고 있었다.
4. **확장 방향 문서 따로 쓰기:** 커뮤니티 규칙 공유, 규칙 거래, 자동화, 업무 양식 보관을 `PRD-vision.md`에 기존 PRD와 분리해서 적었다.
5. **비슷한 서비스 확인:** PromptBase, GPT 스토어를 직접 찾아봤다.

## 2. 이미 있는 것들

| 서비스 | 하는 일 | 믿게 만드는 방식 |
| --- | --- | --- |
| PromptBase | 프롬프트·AI 작업 지침 판매. 약 33만 개, 마켓 판매 수수료 20% | 등록 심사, 별점, 후기 |
| GPT 스토어 | 직접 만든 GPT 공개. 수익 배분은 미국 일부 시범에 그쳤고 지금은 정리 중 | 사용량, 평점 |
| 자동화 템플릿(n8n, Zapier 등) | 흐름 전체를 공유 | 다운로드 수, 후기 |

규칙을 나누는 것도, 파는 것도, 자동화 계획을 보여주는 것도 이미 있었다. 처음엔 "그럼 차별성이 없네" 싶었다.

그런데 표의 마지막 칸을 보면 전부 **말이나 후기**로 믿게 만든다. 실제로 써서 고칠 게 줄었는지는 아무도 기록하지 않는다.

---

## 3. 차별점은 질문에 있다

| 서비스 | 답하는 질문 |
| --- | --- |
| 출처를 보여주는 AI 검색 | 이 내용이 어디서 왔나? |
| ChatGPT 메모리·프로젝트 | 지난번 설명을 기억하나? |
| 프롬프트 마켓 | 남들은 어떻게 시키나? |
| 자동화 도구 | 어떻게 자동으로 돌리나? |
| **또시켰네** | **이 반복 작업, 이제 맡겨도 되나?** |

남의 기능을 가져올지 고민될 때도 이 질문으로 거르면 된다. 출처 표시는 확인할 곳을 줄여 주니까 가져왔고, 자동화 켜고 끄기는 "맡겨볼 만한 때" 다음 단계라서 이어진다. 핵심 질문과 상관없는 기능은 안 가져와도 된다.

다만 아직 **"더 낫다"고 말할 근거는 없다.** 실제 사용자가 써서 고칠 일이 줄었는지 확인하지 않았다. 지금 말할 수 있는 건 "다른 서비스가 안 보는 걸 본다"까지다.

---

## 4. 신뢰는 "높이는" 게 아니라 "맞추는" 것

자동화 연구에서는 신뢰 문제를 **신뢰 보정(trust calibration)**으로 본다(Lee & See, 2004, *Trust in Automation*). 틀릴 수 있는데 다 믿는 과신도, 맞는데 못 믿는 불신도 문제다. 불신하면 매번 전부 다시 확인하게 된다.

보통 쓰는 방법과 또시켰네가 하는 것을 맞춰 보면 이렇다.

| 방법 | 또시켰네 |
| --- | --- |
| 정확도 올리기 | 안 함 (모델 회사 영역). 고친 내용을 규칙으로 쌓는 정도 |
| 근거 보여주기 | 함 (참고한 곳, 자료에 없음) |
| 얼마나 확실한지 알려주기 | 안 함 |
| 써본 경험 쌓기 | 함 (고침/안 고침 기록) |
| 조금씩 넘기기 | 함 (연속 안 고침 → 맡겨볼 만한 때) |

그래서 "신뢰를 만든다"보다 **"믿어도 되는지를 기록으로 판단하게 돕는다"**가 정확한 표현이다.

자동화를 켜고 끄는 방식도 같은 흐름이다. 다만 켜두면 고침 기록이 안 쌓이니까, 켜진 동안에도 가끔 확인하고 고친 게 나오면 다시 매번 확인하게 해야 한다. 연속 횟수 근거로 든 ISO 2859-1 전환 규칙(안정되면 검사를 줄이고, 문제가 나오면 다시 늘림)과 그대로 이어진다.

## 5. 예상 질문에 대한 답

**"애초에 AI가 쓴 내용이 부족하면요?"**
맞다, 결과 품질은 모델에 달려 있다. 부족한 부분을 고치면 다음 실행에 규칙으로 반영되고, 그래도 계속 고쳐야 하면 연속 안 고침이 안 쌓여 "아직 맡기지 마세요"라는 답이 나온다. 이건 실패가 아니라 이 앱이 해야 할 답이다. 단, 자료에 있는데 결과에서 **빠진 내용은 못 잡는다**는 건 인정해야 한다.

**"모델이 낮아서 그런 거 아니에요?"**
모를 일이다. 지금까지 잰 숫자는 전부 `gemini-3.5-flash-lite` 결과이고, 처음 정한 3.8-flash는 503이 반복돼 한 번도 비교하지 못했다. 프롬프트로 확실히 줄인 실수(얼버무림 5→0, 날짜 4→0)도 있고, 프롬프트로도 안 없어진 실수(겹치는 규칙 가리기, 긴 자료 뒷부분 빠뜨리기)도 있다.

## 6. 오늘 배운 것

1. **기능이 겹친다고 차별성이 없는 건 아니다.** 같은 기능이라도 어떤 질문에 답하려고 쓰느냐가 다르면 다른 제품이다.
2. **"없다"는 말은 찾아본 범위까지만 한다.** 처음엔 "현 시점에 없어 보인다"고 생각했지만, 찾아보니 비슷한 게 많았다. 확인한 범위를 같이 적어야 한다.
3. **시장이 있다는 건 수요의 신호이기도 하다.** 프롬프트를 사고파는 곳이 있다는 건, 남이 만든 규칙을 쓰려는 사람이 있다는 뜻이다.
4. **모델은 "제일 똑똑한 것"보다 "조건 안에서 안정적으로 돌고 우리 일에서 실수가 적은 것"으로 고른다.** 비용·약관 → 안정성 → 작업 품질 → 우리 자료로 직접 비교 순서다.
5. **문제 정의는 원인과 결과가 같은 말이면 안 된다.** "못 믿는다 → 신뢰가 떨어진다"는 같은 말을 두 번 한 것이었다.
